# clipboard+ のレビュー結果と試作方針

2026年11月14日。外部レビュー2件を比較し、Appleの一次資料と照合した。以下は開発の推奨順。実機試験は未実施で、数値は試験の目標を示す。

**最初に確かめたいのは「SafariでA・B・Cをコピーし、横に置いた小窓からBだけをメモへ戻せるか」。** タッチ中心の13インチiPad Airで、コピーのたびに保存操作をする手間と、再利用時に入力位置を失う手間の両方を測る。小窓の通常ウインドウ表示とStage Managerを試す。

## レビューの採否

最初の添付をA、2件目をBとする。レビューに渡したブリーフと競合調査は、このリポジトリに含めていない。

| 論点 | AとBの意見 | clipboard+での判断 |
| --- | --- | --- |
| 小窓とタッチ | 両者とも小窓を支持。Aは双方向のドラッグ、Bはタップ後に入力先へ戻る手数を重視 | 両方試す。ドラッグ非対応の入力先ではタップで再コピーして通常の貼り付けを使う |
| 最初の機能 | Aは画像と共有拡張まで含める。Bはテキストの1画面試作を優先 | 先に文章で連続コピーを検証。文章・URLの日常利用版の後に画像と共有拡張を追加する案。共有拡張が入るまでは全画面から共有での保存は提供できない |
| 署名 | Aは無料ではApp Groups不可として有料登録を推奨。Bは未確認 | Appleの表に無料アカウントの対応印がある。試作のために購入を前提とせず、実際に選ぶ署名で両ターゲットのアクセスを確認する |
| 専用キーボード | フルアクセスなしで共有領域を読めるかでAとBの主張が逆 | 現行のApple資料は読み取り可、書き込み不可。導入は後続。読み取り専用の履歴で文章を挿入し、日本語入力に戻れるかを検証する |
| 自動収集とPiP | 両者とも通常の並列表示を優先し、PiPには成立条件があると指摘 | 明示操作と任意の並列収集を先にする。利用者は2026年11月14日にこの判断を一任した。全画面での自動収集は初版の必須条件にしない |
| 保存処理 | 両者ともSQLiteを推奨。Aは本体と拡張がDBに直接書き込み、Bは共有フォルダを経由して本体だけが書き込む案 | 文章版では本体が書き込むSQLiteを第一候補にする。拡張追加時はB案から試す。GRDBの採用や書き込み待ち時間は実測して決める |
| 容量と削除 | Aは通常履歴500件、Bは30日・1,000件。両者とも初期の管理画面を縮小 | 文章版は固定の件数上限を仮置きし、ピンは自動削除から除外。削除直後の取り消しと文章・URLの書き出しを優先する。画像と同時に容量・単一項目上限を導入する |
| OS下限 | Aは18または26以降、Bは26、個人試作は27を推奨 | 主端末の申告OSは27.2.1。「なるべく幅広いiPad」の希望を優先し、17以降は互換性の候補として残す。対応を明示する範囲は実際に試したOS・表示方式で決める |

## 一次資料で決着した点

- **App GroupsとCloudKitでは無料アカウントの扱いが異なる。** Appleの表で列見出しと印を照合すると、App groupsには有料・企業・無料の3列すべてに印があり、iCloud: CloudKitの無料列は空欄だった。無料のPersonal Teamには、実機にインストールするプロビジョニングプロファイルの7日期限がある。試作時に、同じ署名での再インストール後も履歴を開けるか確認する。署名やチームを変える際は先に書き出す。[Appleの対応機能表](https://developer.apple.com/help/account/reference/supported-capabilities-ios) ／ [無料アカウントの条件](https://developer.apple.com/help/account/basics/about-your-developer-account)
- **キーボードのフルアクセスは別の権限。** 適切に構成した共有コンテナは、既定のキーボード拡張から読み取り可能。フルアクセスなしでは拡張から使用回数などを書き戻さない。公開を検討する際は文字入力機能・次のキーボードへの切り替え・フルアクセスなしでの動作も確認する。[Appleのキーボード権限](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard) ／ [審査ガイドライン4.4.1](https://developer.apple.com/app-store/review/guidelines/#extensions)
- **変更番号は履歴そのものを表さない。** Appleは変更通知がまとめられること、再アクティブ化時にも番号が更新されること、端末再起動でゼロに戻ることを説明している。自分の書き込み直後の番号を永久保存して一致したら除外する案には誤除外の余地がある。自己書き込みはセッション中の書き込み情報と実際に受け取った内容・形式で照合し、A→自己コピー→外部Bや、別アプリから同じ文章を再コピーした場合を試す。通知だけの場合と、記録中に限り番号を定期確認する場合を比較する。[AppleのchangeCount](https://developer.apple.com/documentation/uikit/uipasteboard/changecount)
- **手動の保存ボタンと自動収集は操作が異なる。** UIPasteControlは利用者が押した貼り付け用。並列表示中の自動収集には他アプリ由来の内容をプログラムから読む際の許可が関わる。自動収集を選んだときに説明し、許可拒否時も手動保存とドラッグを使える構成にする。Pasteの並列収集は製品事例。clipboard+における通知の時期・取得件数は要測定。[UIPasteControl](https://developer.apple.com/documentation/uikit/uipastecontrol) ／ [PasteのiPadでの収集条件](https://pasteapp.io/help/what-paste-captures)
- **機密項目の自動除外には確認がいる。** Appleの `setItemProviders` の `concealed` 引数は書き込み側の指定で、公式APIメタデータではiPadOS 27.3導入。主端末の27.2.1であらゆる秘密情報を判別できる根拠には使えない。試作から一時停止と削除を提供する。ユニバーサルクリップボード由来の内容も届き得るため、他端末由来と識別できるかは別に検証する。[APIメタデータ](https://developer.apple.com/tutorials/data/documentation/uikit/uipasteboard/setitemproviders(_:localonly:expirationdate:concealed:).json) ／ [UIPasteboard](https://developer.apple.com/documentation/uikit/uipasteboard)
- **PiPには製品事例がある。** バックグラウンドサービスの用途を定めるAppleの2.5.4だけで、個別アプリの審査結果は確定しない。別の動画のPiP、ロック、終了時の記録状態と電池消費を実測できてから採否を決める。[Yoink](https://eternalstorms.at/yoink/ios/) ／ [Appleの審査ガイドライン](https://developer.apple.com/app-store/review/guidelines/#software-requirements)

## 2026年11月14日の見直し

段階1・2と画像の履歴（[段階3の実装方針](段階3の実装方針.md)）は実機試験に合格した。利用者との相談で、以降の順序を次のように変えた。下の「実装の順序と合格条件」の手順3・4より、こちらを優先する。

- **専用キーボードは作らない。** 利用者は純正キーボードを使い続けたい。途中まで作った変更は、ローカルのgit stashに退避してある。入力欄へ直接入れる操作は、本体からのドラッグで代える。
- **最前面に出し続けたいという要望がある。** 利用者がPiPを望む理由は「常に画面の一番上に出ていて使いやすい」ため。PiPの小窓には触れて操作できない（システムの再生操作だけ）と見込まれるため、まずSlide Overで要望を満たせるかを試す。
- **順序。** (1) Slide Overでの使い勝手と自動収集の確認（コード変更なし）。(2) 共有拡張と、画像を含むバックアップ・復元。(3) Slide Overで足りない場合に限り、PiPの技術検証（裏での収集が続くか、触れて操作できるか、審査の見込み）。
- **Slide Overの実機結果（ビルド9、iPadOS 27.2.1）。** 開いている間は、下の全画面Safariでのコピーを全件取り込んだ。画面の端に隠している間は取り込みが止まり、呼び出すと最後の1件だけが入った。clipboard+を開き直すとSlide Overではなくなる。Slide Overへは、左上のウインドウ操作を長押しして「Slide Overを開始」を選ぶ必要があり、Dockから画面の端へドラッグすると画面分割になる。アプリからSlide Overへ切り替える公開APIは見当たらない。
- **見直し後の順序。** Slide Overでは、隠している間の収集と最前面の維持を満たせないため、PiPの技術検証を共有拡張より先に行う（[PiPの技術検証](PiPの技術検証.md)）。検証は小さな試作で、結果を見て採否と共有拡張との順番を決める。
- **その後の経過（2026年11月15日）。** PiPを出していれば全画面でも裏で収集できることを、ビルド11・12で確かめた（[PiPの技術検証](PiPの技術検証.md)）。利用者の判断で、PiPを正式な機能にし（[日常利用の仕上げ](日常利用の仕上げ.md)）、画像を含むバックアップと復元、日数による自動削除を入れ、主な画面を作り直した（[画面の設計](画面の設計.md)）。共有拡張は、PiPで全画面でも収集できるため優先度を下げ、日常的に使って必要になったら作る。現在の状態は [README](../README.md) にまとめてある。

## 実装の順序と合格条件

1. **文章だけの実機試作。** 1列の履歴、記録開始・停止、手動保存、タップでコピー、メモへのドラッグを用意する。Safariを操作しながら識別できる文章20件を約1秒間隔でコピーする。目標は許可設定後に20件が順番どおり各1回残り、途中の1件をメモで再利用でき、繰り返しの許可操作が不要なこと。通常のウインドウとStage Managerで、取得時刻・scene状態・許可表示回数・欠落を比較する。短い間隔でも限界を測る。合わなければ、どの状態で欠落したかを切り分け、手動保存で代用できる範囲を明記する。
2. **文章・URLを日常利用できる版。** 再起動後の保持、双方向ドラッグ、検索、ピン留め、重複整理、削除と取り消し、JSON書き出しを追加。メモへのドラッグと、タップでコピーして戻る操作を比べ、フォーカス・操作数・日本語入力への復帰を確認する。固定の上限を超えてもピンが残ること、書き出した原文・URL・ピンを元データと照合できることを確認する。書き出しだけの段階ではアプリ内復元は未提供。
3. **画像・全画面からの共有保存。** 画像の実体とサムネイルを分け、共有拡張は受け取ったデータにIDを割り当てて一時保存し、書き終えた一式を共有領域で確定する。本体は受信IDで二重処理を防ぎ、起動・前面復帰時および表示中の更新時にDBへ取り込む。受信確定からDB反映までに時間差がある。共有途中・DB反映直後の中断をそれぞれ試し、再開後に欠落・二重登録がないことを確認する。ピンや添付物を含む書き出しと復元をこの段階で検証する。
4. **後続の候補。** 履歴キーボード、順番挿入、日本語OCR、iCloud同期は使用頻度を見て選ぶ。バックグラウンド収集と個別ロックも、それぞれの動作・保護範囲を確認してから提供する。

**開発環境の選択。** 利用者は2026年11月14日にMacを持っていないと回答した。Macなしの経路は[試作1の実装方針](試作1の実装方針.md)に記載した。以下は回答前の整理。Xcodeを使えるMacがあれば、小窓の試作に加え、無料署名で本体・共有拡張の実機試験を進められるか確認する。Macを使えない場合も、お手元のiPadのSwift Playgroundで本体だけの小窓試作を動かせる可能性がある。Appleはアプリを独立したウインドウで実行する手順を案内している。共有拡張・キーボードの追加ターゲットは別のXcode工程として扱う。どちらの経路でも先に上の20件テストを行う。[Swift Playgroundでの実行](https://support.apple.com/guide/playgrounds-ipad/run-your-app-itc650868b1f/ipados) ／ [Apple DTSによる拡張の説明](https://developer.apple.com/forums/thread/771893)
