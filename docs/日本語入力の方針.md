# clipboard+ キーボード拡張の日本語入力方針

> **作らないことにした（2026年11月18日夕方、利用者の判断）。** 試作（AzooKeyKanaKanjiConverter 0.11.2、「かんじ」→「漢字」のテストはCIで通った）は取り除いた。キーボードはクリップボード（履歴とテンプレート）だけを主役にし、英字の面は審査ガイドライン4.4.1のための小さな予備として残す。以下は、その判断の前の下調べの記録として残す。

2026年11月18日。ビルド34の実機試験を受け、[専用キーボードの方針](キーボードの方針.md)を見直して、clipboard+ のキーボード拡張（`ClipboardPlusKeyboard`）に日本語入力（ローマ字・フリック・かな漢字変換）を組み込む方針・下調べ結果・段階設計をまとめる。

この文書では、一次資料やソースコードで確認できた **「確かなこと」** と、実機・CI での実測が必要な **「推測」** を明確に分けて記述する。

## 1. AzooKeyKanaKanjiConverter の概要・導入方法・要件・ライセンス

### 確かなこと

- **現在の版（タグ付きリリースと `main` の違い）:**
  - 最新のタグ付きリリースは **`v0.11.2`**（2026-04-18 公開）。[v0.11.2 リリース](https://github.com/azooKey/AzooKeyKanaKanjiConverter/releases/tag/v0.11.2)
  - 開発ブランチ（`main`）は `v0.11.2` 以降も更新が続いており（2026-11-07 時点）、`ConvertRequestOptions.requireJapanesePrediction` が `Bool` から `PredictionMode` 列挙型へ変更されるなど API の破壊的変更が入っている。[README.md](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/README.md) でも「1.0 まではマイナーバージョン変更で破壊的変更が入り得る」と明記されているため、利用時は版を固定する（今回の試作では `exactVersion: "0.11.2"`）。

## 2. 辞書の入手方法・大きさ・キーボード拡張への入れ方

### 確かなこと

- **入手のしかた（別リポジトリ＋サブモジュール）:**
  - 辞書本体は別リポジトリ [ensan-hcl/azooKey_dictionary_storage](https://github.com/ensan-hcl/azooKey_dictionary_storage) と [ensan-hcl/azooKey_emoji_dictionary_storage](https://github.com/ensan-hcl/azooKey_emoji_dictionary_storage) に置かれ、`AzooKeyKanaKanjiConverter` の `Sources/KanaKanjiConverterModuleWithDefaultDictionary/` 配下に Git サブモジュールとして参照されている。
  - Swift Package の `KanaKanjiConverterModuleWithDefaultDictionary` を選ぶと、SwiftPM がサブモジュールも取得し、リソースバンドル `AzooKeyKanaKanjiConverter_KanaKanjiConverterModuleWithDefaultDictionary.bundle` に自動で同梱する。
  - 一方、テスト用モック辞書 `DictionaryMock`（`Tests/KanaKanjiConverterModuleTests/DictionaryMock`）は「シ」行中心の小規模データであり、一般的な日本語変換テスト（「かんじ」→「漢字」など）には使えない。
- **大きさ（`v0.11.2` サブモジュール参照コミット時点の実測値）:**
  - `Dictionary/` 合計: **25,593,074 バイト（約 25.6 MB、3,397 ファイル）**
    - `Dictionary/louds/`: 22,258,283 バイト（約 22.3 MB、`charID.chid`、`*.louds`、`*.loudschars2`、`*.loudstxt3`。単体最大ファイル `[30AB]0.loudstxt3` は 130,125 バイト）
    - `Dictionary/p/`: 1,212,715 バイト（約 1.2 MB、品詞連接表 CSV）
    - `Dictionary/cb/`: 1,114,056 バイト（約 1.1 MB、連接バイグラム）
    - `Dictionary/mm.binary`: 1,008,020 バイト（約 1.0 MB、意味分類重み行列）
  - `EmojiDictionary/` 合計: **2,973,162 バイト（約 3.0 MB）**
  - 両方の合計: **約 28.6 MB（非圧縮）**。なお `azooKey_dictionary_storage` リポジトリの履歴を含むサイズは約 122 MB（`size_kb: 122125`）。
- **キーボード拡張への入れ方と比較:**

| 方法 | 仕組み | 利点 | 欠点 |
| --- | --- | --- | --- |
| **A. SPM 同梱辞書を拡張バンドルへ入れる（採用）** | `KanaKanjiConverterModuleWithDefaultDictionary` を `ClipboardPlusKeyboard` にリンクし、`.appex` 内の `Bundle.module` から直接読む | 自前リポジトリに約 3,400 個のバイナリを入れなくて済む。本体アプリを開かなくても、またフルアクセスがオフでも最初から変換できる。更新が版の固定に追随する | `.appex` が約 28.6 MB 増える（`EmojiDictionary` 約 3.0 MB も含む）。辞書だけ独立して差し替えにくい |
| **B. 辞書ディレクトリを自前で `.appex` リソースに入れる** | `KanaKanjiConverterModule` を使い、`Dictionary/` のみをリソースとして同梱して `dictionaryURL` で渡す | `EmojiDictionary`（3 MB）を省いたり、語彙を絞ってサイズを削ったりできる | 公開 Git に約 25.6 MB・約 3,400 ファイルを置くか CI で別途ダウンロードする手間が要る。Apache-2.0 の `LICENSE`/`NOTICE` を手動維持する必要がある |
| **C. 本体アプリに置き、App Group 共有コンテナへコピー** | 本体のバンドルから初回起動時に共有コンテナへコピーし、拡張から読む | `.appex` 単体のサイズは小さい | **本体アプリを一度開くまで日本語変換が使えない**。端末上で「本体＋共有コンテナ」に二重保存（約 51 MB）になる。将来の本体・拡張の連携複雑化を招く |

- **判断:** 今回の最小試作と段階1〜3の標準構成は **方法 A（`KanaKanjiConverterModuleWithDefaultDictionary` を `ClipboardPlusKeyboard` のみに同梱）** を選ぶ。`clipboard+` の公開 Git リポジトリを肥大化させず、初回からフルアクセスなし・本体起動なしでも確実に動き、`azooKey` 本番アプリと同じ構成を採れるため。将来アプリ容量や絵文字辞書の有無を細かく削りたくなった場合にのみ方法 B へ移行する。

### 推測（CI・実機で確かめること）

- `ios-build.yml` のビルド時間（サブモジュール取得を含む `xcodebuild -resolvePackageDependencies` の所要時間）と、`.ipa` 書き出し後の圧縮サイズ増分。

## 3. キーボード拡張のメモリ上限と省メモリ設計

### 確かなこと

- **OS の上限仕様と報告例:**
  - Apple の公式ドキュメント（[Extension Overview](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionOverview.html) / [Creating a Custom Keyboard](https://developer.apple.com/documentation/uikit/creating-a-custom-keyboard)）にはキーボード拡張の具体的なメモリ上限 MB 数は公開されていない。
  - 一般的な実務報告・計測記事（Stack Overflow やモバイル開発ブログ）では、古い端末・旧 OS では約 30〜48 MB、近年の端末でも `phys_footprint` が概ね **50〜70 MB** 程度に達すると OS の jetsam によって予告・クラッシュログなしで強制終了（システムキーボードへ強制復帰）されると報告されている。また `com.apple.developer.kernel.increased-memory-limit` 等の増量エンタイトルメントは本体アプリ向けでありキーボード拡張では使えない。
- **`AzooKeyKanaKanjiConverter`（`v0.11.2`）のメモリ節約構造（ソースコード確認済み）:**
  - [DicdataStore.swift](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Sources/KanaKanjiConverterModule/DictionaryManagement/DicdataStore.swift)・[LOUDS.swift](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Sources/KanaKanjiConverterModule/DictionaryManagement/DataStructure/LOUDS.swift)・[extension LOUDS.swift](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Sources/KanaKanjiConverterModule/DictionaryManagement/DataStructure/extension%20LOUDS.swift)・[Dicdata Format](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Docs/dicdata_format.md) による事実:
    1. **LOUDS 簡潔データ構造＋1 バイト CharID:** Trie 木をビット列（`.louds`）と 1 バイト文字 ID（`.loudschars2`）で表現し展開サイズを抑えている。
    2. **遅延読み込み（`preloadDictionary: false` が既定）:** `KanaKanjiConverter.withDefaultDictionary()` の初期状態では `louds/charID.chid`（527 バイト）と `mm.binary`（約 1.0 MB → `Float16` 配列約 0.5 MB）だけを読み込み、各先頭カナごとの `.louds` / `.loudschars2` と連接表 `p/pc_*.csv` は実際に入力された文字分だけ都度読み込む。**逆に `preloadDictionary: true` を渡すと全 `.louds` と全 `.loudstxt3` を一括で RAM に載せるため、キーボード拡張では絶対に `false` を維持する必要がある。**
    3. **`.loudstxt3` の非キャッシュ＋メモリマップ:** `preloadDictionary == false` の場合、候補データの本体が入る `.loudstxt3` はメモリに常駐キャッシュせず、参照のたびに `Data(contentsOf: url, options: [.mappedIfSafe])` で部分的に読み出す。
    4. **Zenzai 無効化:** GGUF ニューラルモデルのロードを避けることで巨大バッファ（数十 MB 級）を防ぐ。
- **`azooKey` 本体での追加対策（ソースコード確認済み）:**
  - `UIInputViewController` のインスタンスがホストアプリ側のコンテキストごとに複数生成されて解放されにくい iOS の挙動に対し、`azooKey` ではエンジン・状態（`KeyboardActionManager` / `InputManager`）を `static` 共有にしてインスタンスごとの重複確保を防ぎ、ロード済みインスタンス数が閾値（15）を超えたら再起動させるワークアラウンドを採っている（[view_controller_memory_leak.md](https://github.com/azooKey/azooKey/blob/main/docs/view_controller_memory_leak.md)）。
  - また `azooKey` の `Keyboard` ターゲットでは `Debug` 構成でも `SWIFT_OPTIMIZATION_LEVEL = "-O"` にしている。

### 推測（実機で確かめること）

- `clipboard+` ではすでに履歴 JSON（最大 2 MB）と SwiftUI 一覧（`LazyVStack` / `LazyVGrid`）を同じ拡張プロセス内に載せている。日本語入力と履歴一覧を長時間交互に使ったときの合計 `phys_footprint` が iPhone と iPad Air 13インチの実機でどの程度になるか（Xcode Instruments の Allocations / VM Tracker 相当または実機長押し入力での安定性確認が必要）。
- `DicdataStore` にはキャッシュ済みの `loudses` や `ccLines` を外部から個別に空にする公開メソッドがないため、`didReceiveMemoryWarning()` 時に未確定文字が空であれば `KanaKanjiConverter` インスタンスを解放・再生成する設計でメモリが戻るか。

## 4. 学習データとユーザー辞書の保存場所（フルアクセス有無）

### 確かなこと

- **学習ファイルの仕様:**
  - [Docs/learning_data.md](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Docs/learning_data.md) によると、学習データは `ConvertRequestOptions.memoryDirectoryURL` で指定したディレクトリに `memory.louds`、`memory.loudschars2`、`memory.loudstxt3`、`.memorymetadata` として保存される（`updateLearningData(_:)` 後に `commitUpdateLearningData()` で永続化、中断時は `.pause` と `.2` 一時ファイルから復旧）。
- **フルアクセス有無によるコンテナの書き込み可否:**
  - Apple の仕様（[Configuring Open Access for a Custom Keyboard](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard)）により、フルアクセスがオフのとき、キーボード拡張は **App Group 共有コンテナを読むことはできるが書くことはできない**。一方、**キーボード拡張自身のサンドボックス内コンテナ（`Library` や `Documents`）にはフルアクセスなしでも読み書きできる**。
  - 実際 `azooKey` でも `InputManager.swift`（[InputManager.swift](https://github.com/azooKey/azooKey/blob/main/Keyboard/Display/InputManager.swift)）で学習データの保存先 `memoryDirectoryURL` に拡張自身の `Library` ディレクトリ（`FileManager.default.url(for: .libraryDirectory, in: .userDomainMask, ...)`）を使い、共有コンテナ（App Group）をフォールバックにしている。
- **clipboard+ での保存場所の方針:**
  - **学習データ（`memoryDirectoryURL`）:** キーボード拡張自身のサンドボックス内 `Library/Application Support/KanaKanjiMemory`（フルアクセスがオフでもオンでも同じ場所に保存・学習できる）。
  - **本体アプリからの学習リセット:** 本体アプリから拡張自身の `Library` へは直接触れないため、App Group の `keyboard-settings.json`（本体が書き、拡張が読む。フルアクセス不要）に `learningResetVersion`（またはタイムスタンプ）を持たせ、拡張側が前回処理した値より増えていたら `converter.resetMemory()` を呼ぶ仕組みにする。
  - **ユーザー辞書（`sharedContainerURL`）:** 本体アプリで編集して App Group 共有コンテナへ書き出し、キーボード拡張は `sharedContainerURL` から読み取り専用で参照する（`user.louds*`）。

### 推測（実機で確かめること）

- iOS 27 実機でフルアクセスオフの状態において、拡張から App Group 共有コンテナの読み取り（`keyboard-history.json` と将来の `user.louds*`）と、拡張自身の `Library` への学習ファイル書き込みが問題なく通ること。

## 5. 入力・未確定文字列・候補帯・確定・カーソル移動・面の切り替えの作り方

### 確かなこと（API と `azooKey` の知見）

- **ローマ字（QWERTY）からかなへの変換:**
  - `ComposingText` に `insertAtCursorPosition(key, inputStyle: .roman2kana)` で 1 文字ずつ渡すと、内蔵の `InputTables.defaultRomanToKana` により `k` → `ka` → `か`、`nn` → `ん`、`xtu` → `っ` 等へ逐次変換される（[ComposingText ドキュメント](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/v0.11.2/Docs/composing_text.md)）。
  - 見かけの未確定文字列は `composingText.convertTarget`、カーソル位置は `composingText.convertTargetCursorPosition` で得られる。
- **フリック（12キー）のかな入力:**
  - フリック入力で確定したひらがな 1 文字を `composingText.insertAtCursorPosition(kana, inputStyle: .direct)` で渡す。
  - `゛゜小` キーは `composingText.convertTargetBeforeCursor.last` を参照し、濁音・半濁音・小書きへ変換可能であれば `deleteBackwardFromCursorPosition(count: 1)`＋`insertAtCursorPosition(置換後文字, inputStyle: .direct)` で差し替える（`azooKey` の `InputManager.changeCharacter` と同じ方式）。
- **未確定の文字の扱い（`textDocumentProxy.setMarkedText`）:**
  - `UITextDocumentProxy` は iOS 8 以降で `setMarkedText(_:selectedRange:)`（[Apple 公式ドキュメント](https://developer.apple.com/documentation/uikit/uitextdocumentproxy/setmarkedtext(_:selectedrange:))）と `unmarkText()`（[Apple 公式ドキュメント](https://developer.apple.com/documentation/uikit/uitextdocumentproxy/unmarktext())）を備える。
  - ただし実アプリ（WebView や独自テキスト欄）や OS 更新では、`markedText` 上をタップした際の挙動や `textDidChange` 通知のタイミングに癖があることが知られており、`azooKey` でも `DisplayedTextManager`（[DisplayedTextManager.swift](https://github.com/azooKey/azooKey/blob/main/AzooKeyCore/Sources/KeyboardExtensionUtils/DisplayedTextManager.swift)）において、`NSString` の UTF-16 長で `selectedRange` を計算し、ホスト側の外部編集と競合したとき（iOS 27 対応を含む）に `unmarkText()` や状態リセットへ倒す制御、および `markedText` オフ時（`deleteBackward` + `insertText` 差し替え）の切り替えを持っている。
  - **clipboard+ の方針:** 既定では `setMarkedText(_:selectedRange:)` を使い、同時にキーボード上部の候補帯の上（または先頭）にも必要なら未確定読みを確認できる表示を検討する。`textDidChange(_:)` で外部からの移動・確定を検知したら、未確定状態を安全に確定またはリセットする。また一部アプリでの不具合に備え、設定で従来の `insertText`/`deleteBackward` 方式に落とせる余地を残す。
- **変換候補の帯・確定・カーソル移動:**
  - **候補帯:** キー面の上端に高さ約 36〜40pt の横スクロール候補バーを置く（必要時は一覧展開ボタン）。`converter.requestCandidates(composingText.prefixToCursorPosition(), options: ...)` の `mainResults` を並べる。
  - **確定:** 候補タップ時は `composingText.prefixComplete(composingCount: candidate.composingCount)` を呼ぶ。残りの未確定文字が空になれば確定文字（`insertText` / `unmarkText`）を入れて `converter.stopComposition()` を呼び、先頭文節だけ確定して残りがある場合は `insertText(candidate.text)`（または残りを `setMarkedText` で再表示）＋`converter.setCompletedData(candidate)` のあと残りで再変換する。
  - **カーソル移動:** 未確定文字がある間は `composingText.moveCursorFromCursorPosition(count:)` と `setMarkedText` 内の `selectedRange` 更新、未確定文字が空のときは `textDocumentProxy.adjustTextPosition(byCharacterOffset:)`（UTF-16 単位の調整）を使う。
- **clipboard+ の履歴・テンプレートの面との切り替え:**
  - 現在の `KeyboardMode`（`.list` / `.alphanumeric`）を拡張し、`.list`（履歴・テンプレート）、`.japanese`（ローマ字／フリック）、`.alphanumeric`（英数字・記号）を持つ形にする。
  - 下段のバーや上段タブからワンタップで `.list` ↔ `.japanese` ↔ `.alphanumeric` を行き来できるようにする。
  - 面を切り替える直前に未確定文字がある場合は、`unmarkText()` 相当で確定してから履歴やテンプレートの挿入（`insertText`）へ移ることで、未確定文字列が消えたり混ざったりする事故を防ぐ。

### 推測（実機で確かめること）

- `KeyboardLayoutMetrics.preferredHeight`（現在 iPhone 縦 284pt・横 204pt・iPad 316〜340pt）に候補帯約 36〜40pt を足した場合、既存の高さ内でキータッチ領域が窮屈にならないか、あるいは候補帯分だけ高さを調整すべきか（特に iPhone 横向き 204pt 時の押しやすさ）。
- 12キーフリックのジェスチャー感度（ドラッグ開始閾値・斜め誤爆の防ぎ方・連続タップ時の遅延なし確定）の実機操作感。

## 7. 審査ガイドライン 4.4.1 との関係

### 確かなこと

- Apple App Store Review Guidelines 4.4.1（[Extensions](https://developer.apple.com/app-store/review/guidelines/#extensions)）はカスタムキーボードに以下を求める。
  1. 文字入力機能を提供すること。
  2. 次のキーボードへ切り替える手段（地球儀キー等）を提供すること。
  3. **ネットワークアクセスやフルアクセスなしでも動作すること。**
  4. 収集したユーザー操作情報は端末内のキーボード機能向上のみに使うこと。
  5. 広告・課金・設定アプリ以外の他アプリ起動・キー本来の目的外の流用（例：改行キーを別機能にする）をしないこと。
- **clipboard+ への適合方針:**
  - `AzooKeyKanaKanjiConverter`＋同梱辞書は完全に端末内オフラインで動き、通信もフルアクセスも使わずに文字入力とかな漢字変換ができる。
  - 学習データの保存先を拡張自身の `Library` コンテナに置くため、学習もフルアクセスなしで動く。
  - 既存の「今のコピーを保存」（`UIPasteControl` / `UIPasteboard`）だけがフルアクセス前提であり、すでに `hasFullAccess == false` 時は非表示にしていて 4.4.1 に沿っている。

## 8. 公開リポジトリに第三者のコードと辞書を入れるときの扱い

### 確かなこと

1. **Swift Package Manager 参照を使う場合（今回の試作・標準構成）:**
   - 第三者のコードや辞書バイナリそのものは clipboard+ の Git リポジトリへ複写しない（公開リポジトリの履歴肥大化と著作権ファイル管理の手間を避けられる）。
   - それでもリポジトリおよびビルド成果物が MIT / Apache-2.0 のソフトウェア・辞書を利用するため、リポジトリルートに [THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md) を置き、配布アプリ内（`SettingsView`）にもライセンスと著作権表示を載せる。
2. **もし辞書ファイルや第三者コードをリポジトリ内に直接置く場合（カスタム辞書等へ切り替える場合）:**
   - 元の `LICENSE`・`NOTICE` ファイルを削除・改変せず、配置したディレクトリ内（例：`app/ClipboardPlusKeyboard/Dictionary/LICENSE`）またはルート `THIRD_PARTY_LICENSES.md` に明確に残す。
   - Apache-2.0 第 4 条に基づき、改変を加えたファイルには変更した旨の表示を残す。
   - `azooKey_dictionary_storage` は約 3,400 ファイル・約 25.6 MB あるため、直接コミットする場合は Git リポジトリ肥大化に留意する（CI でのリリース時取得や SwiftPM のまま維持するのが望ましい）。
