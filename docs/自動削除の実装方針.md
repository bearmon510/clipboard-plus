# clipboard+ 日数による自動削除の実装方針

2026年11月15日。利用者の提案で、一定の日数を過ぎた履歴を自動で消す機能を入れる。パスワードなどの秘密情報が、気付かないまま長く残ることを防ぐため。秘密の印が付いた内容は保存しない処理（[PiPの技術検証](PiPの技術検証.md)）があるが、印のない秘密情報は判別できない。

## 決めたこと

| 項目 | 内容 |
| --- | --- |
| 設定 | 「自動削除」：しない／1日／7日／30日／90日 |
| 初期値 | 30日（2026年11月15日に利用者が了承） |
| 基準の日時 | 最後に収集した時刻。何度も使う項目は残る |
| 対象 | ピン留めしていない文章・URL・画像。ピン留めは消さない。取り消し待ちの項目は、既存の期限で消える |
| 実行の時機 | 起動時、前面に戻ったとき、起動中は1時間ごと |
| 記録 | 計測ログに消した件数を残す。内容は残さない |
| 取り消し | なし。手動の削除と違い「元に戻す」は出さない |

- 既存の上限（ピン留め以外1,000件、画像合計500MB）はそのまま残し、日数の条件と両方で働かせる。
- 画像のファイルは、既存の削除の仕組み（削除の通知とファイルの後始末）で消す。
- 設定を変えたら、その場で新しい日数を適用する。
- 初期値を30日にするので、更新後の最初の起動で30日より古い履歴が消える。設定画面にこの動作を書く。

## バックアップからの復元との関係

期限を過ぎた項目を復元すると、すぐに自動削除の対象になる。復元の確認画面に「期限を過ぎているため削除される件数」も出し、反映後の実際の件数と一致させる。

## 合格条件

1. 最後に収集してから30日を過ぎた、ピン留めしていない項目が消える。ピン留めの項目は残る。
2. 「しない」にすると、日数では消えない。
3. 設定を短くすると、その場で対象が消える。
4. 画像の項目が消えると、画像ファイルも消え、設定の使用量が減る。
5. 復元の確認画面の「期限で削除される件数」が、実際に消えた件数と一致する。

日数の判定は、時刻を差し替えられる単体テストで確かめる。

## 実装メモ

0.4.0のバックアップ・復元実装に追加。外部ライブラリ、DBスキーマ、バックアップ形式の変更なし。`app/project.yml`の`MARKETING_VERSION`は`"0.4.0"`のまま。

- **設定と日数。** `HistoryRetention`に5つの選択肢・表示名・秒数を集約。`UserDefaults`の`historyRetentionDays`へ保存し、未設定・不正値は30日。「しない」は期限なし。1日は24時間とし、暦日や日付の切り替わりでは判定しない。
- **通常の削除。** `HistoryDatabase.purgeHistory(olderThan:)`で、取り消し待ちでなく、ピン留めでなく、最終収集時刻が境界より厳密に古い行を削除する。境界と同時刻は残す。既存の`now`、トランザクション、`removeRows`、`takeRemovals`を使用し、取り消し待ちは既存の5秒の期限で消す。
- **実行と画面更新。** `HistoryStore`の直列キューで、読み込み時、sceneのactive遷移、設定変更時に強制実行。既存の1秒タイマーでは前回の成功から3,600秒以上で実行し、失敗時は前回時刻を進めず再試行する。時計が戻った場合も再判定する。前面復帰は実行中の後始末があってもキューへ積む。削除通知で一覧から除き、既存の画像掃除・使用量更新へ接続。ドラッグ・バックアップで保護中のファイルは保護解除後に掃除する。1件以上の削除時だけ「期限による自動削除」と件数・設定日数を記録し、内容をログへ渡さない。
- **復元。** 共通の復元計算を「マージ→期限→件数上限→画像容量上限」の順にした。マージ後の新しい収集日時とピンを使い、既存履歴も含めて判定する。期限と上限の削除件数は重複させず、確認画面と結果で分ける。反映時の再見積もりと実際の反映には同じ境界時刻を渡す。確認中の収集・設定・時刻の変化で件数が変わった場合は、復元を反映せず検証済みファイルを保持し、新しい見積もりの確認へ戻す。これは従来の「反映後に見積もりとの差を知らせる」動作からの変更で、確認した件数と実績を一致させるため。成功・取消・失敗のファイル掃除と巻き戻しは従来の仕組みを使う。
- **設定画面。** 「履歴の保存」にメニュー式Pickerと折り返す説明を追加。基準日時、ピンの保護、取消不可、期間短縮時の即時削除、初期値30日と更新後の初回起動時の削除を明記。手動削除だけが5秒間取り消せることも区別した。
