# テンプレートと連続貼り付けの方針（0.12.0）

2026年11月16日、利用者と決めた内容。

## 利用者の判断

- テンプレートは、新しい一覧を作らずに**ピン留めを強化する**（案B）。ピン留めは自分で外すか消すまで残るため、定型文の置き場として使える。
- 連続貼り付けは、**相手のアプリが貼り付けたら自動で次へ進める**。うまく動かない場面に備えて「次へ」ボタンも付ける。

## テンプレート（ピン留めの強化）

1. **自分で書いて追加する。** ピン留めの見出しに「＋」を置く。名前（任意）と本文を書くと、ピン留めした文章として入る。
   - 同じ本文の履歴がすでにあれば、新しく作らない。その項目をピン留めし、名前を付ける。
   - 由来は `HistorySource.written`（新設）。自動収集・手動保存・ドラッグ・切り取りと区別する。
2. **名前を付ける。** 文章・リンク・画像・ファイルのどれにも付けられる。カードでは名前を本文の上に出す。検索の対象にする。
3. **書き直す。** 文章とリンクの本文を編集できる。種類（文章かリンクか）は書き直した本文から判定し直す。
   - 書き直した本文が、ほかの項目と同じになる場合は保存しない。「同じ内容の項目がすでにあります」と伝える。
4. **並べ替える。** ピン留めの並びは、自分で決めた順にする。再びコピーしても並びは動かない。
   - 新しくピン留めしたものは先頭に入る。
   - 並べ替えは専用の画面（一覧をドラッグで並べ替える）で行う。カードは他のアプリへドラッグできるので、カードの上での並べ替えとは衝突させない。
5. **ショートカットとSiri。** 名前でピン留めを探してコピーできるようにする。既存の「履歴をコピー」の検索で名前も照合し、表示名に名前を使う。

### データ

- スキーマ4：`title TEXT`（空はNULL）と `pin_order INTEGER`（ピン留めのときだけ値を持つ）を追加する。
  - 移行時は、既存のピン留めに今の表示順（`collected_at DESC, id DESC`）で番号を振る。
- ピンを外すと `pin_order` はNULLにする。名前は残す。
- バックアップは名前とピン留めの順も含める。古い版が新しいバックアップを読めるかどうかは、互換性を確かめてから決める。読めない場合は形式番号を上げ、古い版でははっきり拒否させる。

## 連続貼り付け

### 使い方

1. カードのメニューで「連続貼り付けに追加」を選ぶ。選んだ順に並ぶ。対象は文章とリンク。
2. 画面の下に、並べたものと「開始」「次へ」「やめる」の帯が出る。
3. 開始すると1つ目がクリップボードに入る。相手のアプリで貼り付けると、次の項目が自動で入る。最後まで貼ったら終わる。

### 貼り付けを知る仕組み

- iPadOSには、他のアプリが貼り付けたことを知らせる公開APIがない。
- そこで、クリップボードへ入れるときに中身をその場で渡さない（`NSItemProvider` の遅延読み込み）。相手のアプリが中身を求めた時点で読み込み処理が呼ばれるので、それを「貼り付けた」とみなす。中身を渡し終えた後で、次の項目を入れる。
- 1回の貼り付けで、複数の形式が読まれることがある。1回の書き込み（changeCount）につき、進めるのは1回だけにする。
- clipboard+自身の監視が中身を読むと、貼り付けたと誤って判定してしまう。連続貼り付けで入れた書き込みは、監視で中身を読まない。

### 危険と確かめること

- **アプリが止まっている間：** 遅延読み込みは、clipboard+が動いている間しか答えられない。小窓やSlide Overで画面に出したまま使う前提にする。アプリが裏へ回ったら一時停止し、戻ったら今の項目を入れ直す。
- **中身を先に読むアプリ：** 貼り付ける前に中身を読むアプリや、iPadOSの機能（ユニバーサルクリップボードなど）があると、貼っていないのに次へ進む。「次へ」のほか「戻る」も付けて、手で直せるようにする。
- **計測ログ：** 読み込みが求められた時刻、型、そのときの状態を残す。本文は残さない。実機での判断材料にする。

## 作業の分け方

- データと仕組み（スキーマ4、作成・名前・書き直し・並べ替え、バックアップ、検索、ショートカット、連続貼り付けの仕組みとテスト）はCodexに依頼する。
- 画面（追加・編集の画面、並べ替えの画面、カードの名前、連続貼り付けの帯、メニュー）はClaudeが書く。

## 実装メモ（0.12.0・データ層とエンジン）

### 保存と編集

- スキーマ4で `title` と `pin_order` を追加した。移行はトランザクション内で行い、既存のピンを `collected_at DESC, id DESC` 順に0から採番する。取り消し待ちの削除項目にも番号を付ける。
- 新しいピンは最小の番号から1を引いて先頭へ置く。整数の下限に達していた場合だけ採番し直す。並べ替えでは0から振り直し、指定されなかったピンは現在の相対順で後ろへ置く。重複ID・ピンでないIDは無視する。
- 名前は前後の空白・改行を除き、Swiftの文字単位で100文字まで。空はSQLのNULL。ピンを外しても名前は残り、再収集では名前・ピン順を変更しない。削除の取り消しでも復元する。同じ本文が取り消し待ちの間に再収集された場合は、元の名前・ピン順を優先し、従来どおり日時と回数を統合する。
- 作成・編集の空判定は空白・改行だけの本文も含む。それ以外の本文の空白や改行は保持する。既存本文への作成はID・由来・日時・回数を保持し、ピンと指定された名前だけ変更する。作成の `title: nil` は既存名を保持し、空文字を指定すると名前を消す。編集の `title: nil` は名前を消す。
- 編集の重複判定はSQLiteのBINARY比較を使い、本文・名前とも何も変更せず `.duplicate` を返す。編集に成功してもID・ピン・ピン順・回数・日時・由来は維持する。

### UIから使うAPI

`ClipboardMonitor` の次のAPIはすべてMainActor上で使う。保存キューからの反映で `entries` を更新してから、作成・編集の完了コールバックを呼ぶ。

```swift
func createWritten(text: String, title: String?, completion: @escaping (Result<HistoryEntry, HistoryEditError>) -> Void)
func setTitle(_ title: String?, for entry: HistoryEntry)
func editText(_ entry: HistoryEntry, text: String, title: String?, completion: @escaping (Result<HistoryEntry, HistoryEditError>) -> Void)
func reorderPins(_ orderedIDs: [Int])

func enqueueForPaste(_ entry: HistoryEntry)
func removeFromPasteQueue(id: Int)
func startPasteQueue()
func advancePasteQueue()
func rewindPasteQueue()
func stopPasteQueue()
```

- `HistoryEditError` は `.empty` / `.duplicate` / `.unsupportedKind` / `.failed`。表示には日本語の `message` を使う。名前変更・並べ替えの保存失敗は既存の `storageError` に出す。
- `HistoryEntry.title` と `pinOrder` はOptional。既存の初期化呼び出しや古いJSONのデコードは維持した。`displayTitle` は前後の空白を除いた表示用の名前で、空ならnil。
- `EntrySections.make` と `.pinned` フィルターは番号の昇順、nilは末尾。同じ番号・nil同士は入力順を維持する。他のセクションの順序は変えない。
- 検索は全種類の名前も対象。ショートカットの表示名にも名前を使い、検索では名前の完全一致（大文字小文字を区別しない）を先頭にする。AppIntentsの保存プロパティと `@Property` の初期化順序は変えていない。

### バックアップ互換性と復元

- 0.11の `HistorySource` は `written` をデコードできない。また、新しいOptionalキーを無視すると名前・ピン順を失う。このため、名前・ピン順・`written` のどれかを含むバックアップは**形式3**で書く。旧版はJSONを読む前のヘッダー検査で「このバックアップの版には対応していません。」として拒否する。
- 新機能の情報がない場合は従来どおり形式1（ファイルなし）／2（ファイルあり）で書く。新版の読み込みは形式1〜3に対応する。別機能のJSON書き出しは、同じ条件で形式4に上げ、それ以外では従来の2／3を保つ。
- 復元で同じ本文・添付がある場合、端末の空でない名前を優先し、名前がなければバックアップの名前を使う。ピンは従来どおり両方の和集合にする。
- 端末の既存ピンを現在の相対順で先頭に保ち、新たにピンになる項目をバックアップ内のピン順で後ろへ追加する。古いバックアップの番号なしピンは収集日時の降順、同日時はID降順。全体を0から採番し直すため、番号の値自体は変わり得る。既存項目の採番変更も復元見積もりの更新件数に含める。同じバックアップの再復元では順序は変わらない。
- 画像・ファイルの復元でローカルの添付名を差し替える際にも、名前・ピン順を引き継ぐ。

### 連続貼り付けの状態と監視

- `ClipboardMonitor.pasteQueue` は `@Published private(set)`。`PasteQueueState` は `entryIDs`、0始まりの `currentIndex`、`isRunning`、`isPaused`、`lastAdvance` を持つ。未開始ではindexはnil。一時停止中も `isRunning` はtrue。最後まで届けるとfalseにし、リスト・最後のindex・最後のクリップボード内容は残す。「やめる」は状態をすべて初期化し、クリップボード自体は消さない。
- `Services/PasteQueue.swift` が状態と遅延プロバイダーを管理する。本文は `public.utf8-plain-text`、リンクは加えて `public.url` で提供する。`suggestedName` はnilのまま。
- 読み込み要求にデータを返した後、MainActorで短い遅延を置いて次へ進む。書き込みごとの識別子と `changeCount` で、複数形式・重複要求・古いプロバイダーへの遅れた要求から二重に進むことを防ぐ。
- 書き込みは既存の `ClipboardPasteboard.writeFileProviders` を通す。監視には専用の自己コピー `changeCount` を残し、型や本文を読む前に除外する。この印は完了・停止後も現在のクリップボードが同じ間は有効で、履歴の追加や回数増加を起こさない。
- 外部コピーとバックグラウンド移行で一時停止する。停止中の「次へ」または「開始」は現在の項目を入れ直す。通常の「次へ」は次へ進め、「戻る」はひとつ前を入れ直す。active復帰でも実行中なら現在の項目を入れ直す。書き込み失敗も一時停止としてログに残す。
- 通常の履歴記録が無効でも、実行中のキューは0.5秒間隔で外部変更を確認する。履歴の削除・全消去・自動削除による一覧更新時に、失われたIDをキューから落とす。現在の項目が消えたら後続を入れ、後続がなければ終了する。
- 作成・名前・編集・並べ替えと、キューの開始／停止／送り／戻る／一時停止／再開／各読み込み要求を計測ログへ記録する。キューの読み込み要求には形式・書き込みのchangeCount・処理時scene・index・要求時刻を含める。これらの新しいイベントには本文も名前も渡さず、ログの冒頭表示を有効にしても含めない。

### 検証と残る確認

- XCTestに移行、作成・重複編集・種類の再判定・保持する項目、名前のNULL化と文字数制限、並べ替え・再収集・ピン解除・取り消し、表示順・名前検索、バックアップ互換性と再復元、エンティティ／クエリ、キューと監視のテストを追加した。
- プロバイダーの読み込みは偽のペーストボードに実際に渡した `NSItemProvider.loadDataRepresentation` を呼んで模擬する。MainActorのテストは同期のXCTestメソッド内でexpectationを待ち、asyncテスト内では `wait(for:)` を呼ばない。
- Windows上で実装SQLを抽出し、SQLiteで移行・作成・編集・一意制約によるロールバック・ピン解除・NULL保存とSQLの準備を確認した。SwiftビルドとXCTest実行は未実施で、push後のXcode 27.1 CIで確認する。コミット・pushはしていない。
- 実機ではSlide Over／小窓での遅延読み込み、宛先アプリによる先読みや複数形式要求、URLの貼り付け、ユニバーサルクリップボード、バックグラウンドからの復帰、実際の `setItemProviders` とchangeCountの挙動を確認する必要がある。読み込み要求は貼り付けの代用指標なので、誤送りは「戻る」「次へ」で修正する。UIは後続作業。
