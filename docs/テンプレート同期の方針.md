# テンプレート同期の方針

2026年11月18日。利用者の判断に基づき、iPad・iPhone と Windows PC のすべての端末でテンプレートを使えるようにし、**「同期」ボタンを押したときだけ同じテンプレートにそろえる**仕組みを設計する。

この文書では、**今のコードで確かなこと**（リポジトリルートからの相対パスと行番号付き）と、これから作る**提案**を分けて記す。

---

## 1. 使い方と全体の流れ

### 今のコード（確かなこと）

- **接続の形**：PC が待ち受け（GATT サーバー／peripheral）、iPad・iPhone がつなぎに行く側（central）である（`docs/Windows同期の方針.md:17`）。1つの QR コード（共有鍵）で複数の iPhone・iPad を PC に登録でき、PC は認証済みの端末 ID ごとに接続と送信待ちを管理する（`windows/ClipboardPlus.Windows/Core/SyncRepository.cs:28-30`、`windows/ClipboardPlus.Windows/Core/SyncCoordinator.cs:340-350`）。iPad と iPhone は直接通信せず、PC 側も今の履歴同期では端末間の中継をしていない（`docs/Windows同期の段階3メモ.md:3`）。
- **iOS のテンプレート画面**：`app/ClipboardPlus/Views/ContentView.swift:334-368` の `paneBar` に「履歴｜テンプレート」の切り替えがあり、「テンプレート」を選んだときは右端に新規作成の「＋」ボタン（`353-363` 行）だけが並んでいる。画面下部にはトースト通知と削除取り消し帯を出す `bottomOverlay`（`725-746` 行）がある。
- **PC の履歴の窓**：`windows/ClipboardPlus.Windows/HistoryWindow.xaml:194-485` は、見出し帯（`203-222` 行）・検索欄（`225-261` 行）・通知帯 `NoticeBanner`（`264-287` 行）・カード一覧 `HistoryList`（`290-451` 行）・下部案内帯（`472-484` 行）の5段構成で、まだテンプレートの切り替えはない。

### 提案

1. **同期ボタンを置く場所**
   - **iOS**：`ContentView` の「履歴｜テンプレート」切り替え帯（`pane == .templates` のとき）の右端、「＋」ボタンの左隣に**同期ボタン**（回転矢印アイコン、`accessibilityLabel("テンプレートを同期")`）を置く。PC と組んでいないとき（`status == .unpaired`）は出さず、組んでいるときは常に出す。未接続のまま押されたときはボタンを消さずにトーストで理由（「PCとつながっていません。PCの近くで試してください」「Bluetoothがオフです」など）を知らせる。
   - **PC**：`HistoryWindow` の見出し帯と検索欄の間に「履歴｜テンプレート」の切り替え帯を新設し、「テンプレート」を選んだときはその右端に**「同期」ボタン**と**「＋」ボタン**を並べる。つながっている端末が0台のときに押されたら `NoticeBanner` に「つながっているiPhone・iPadがありません」と出す。

2. **押したときに起きること**
   - 普段テンプレートを追加・編集・並べ替え・削除しただけでは通信しない。「同期」ボタンを押したときだけ、手元のテンプレート一覧（削除の印を含む）と相手のテンプレート一覧を突き合わせて統合し、双方を同じ状態に保存する。
   - 同期中は同期ボタンをスピナー表示（押下不可）にし、終わったらトースト（iOS）または `NoticeBanner`（PC）に件数を短く出す。

3. **PC を中継役にする流れ（iPad → PC → iPhone）**
   - **この流れでよい（採用する）。** PC 自身がテンプレートを保存して使うため、PC がそのまま共通の置き場（ハブ）になる。
   - **iPad（または iPhone）で押したとき**：その端末と PC の2台だけをその場でそろえる。たとえば iPad で追加・編集して「同期」を押すと PC に反映され、そのあと別の時刻に iPhone で「同期」を押すと、PC に保存されている iPad 分も含めて iPhone と PC がそろう。たまたま裏でつながっている他の端末へ勝手に自動配信はしない（「ボタンを押したときだけそろえる」方針を守り、裏にいる端末の意図しない書き換えや背景通信のタイムアウトを避けるため）。
   - **PC で押したとき**：その時点で認証済みで**つながっている端末すべて**と1回の操作でそろえる。iPad と iPhone の2台が同時につながっているときに片方へ古い結果が渡らないよう、PC は **2段階（集めてから配る）** で動く：
     1. つながっている全端末へ一覧要求を送り、全端末分のテンプレート一覧を受け取って PC 上でまとめてマージし（`PC ∪ iPad ∪ iPhone`）、PC に保存する。
     2. 確定した統合済みの一覧を、参加した全端末へ送り返す。
     （1台だけつながっているときは1往復で終わり、途中で切れた端末があれば応答した端末分だけで完了させて件数を知らせる。）

## 2. そろえ方の決まり

### 今のコード（確かなこと）

- **識別子**：iOS の `HistoryEntry.id` は端末ごとの SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`（`app/ClipboardPlus/Core/HistoryDatabase.swift:45`）であり、端末間で共通ではない。Siri・ショートカットの `TemplateEntryEntity` はこの整数 `id` で項目を参照する（`app/ClipboardPlus/Services/HistoryEntryEntity.swift:116-138`）。
- **一意制約**：iOS の SQLite スキーマ 5 は、有効なテンプレート（`pinned = 1 AND deletion_id IS NULL`）の中で同じ本文を1件しか許さない一意インデックス `history_active_text`（UTF-8 バイト完全一致）を持つ（`HistoryDatabase.swift:109, 237, 256`）。
- **名前・タグ・並び順**：`title` は前後空白を除いて最大100文字、空なら `nil`（`app/ClipboardPlus/Core/HistoryEntry.swift:121-125`）。`tag` は前後空白を除いて最大30文字、空なら `nil`（「その他」）（`HistoryEntry.swift:127-132`）。グループの並びはタグ名の自然順（`localizedStandardCompare`）で「その他」が最後、グループ内の並びは `templateOrder` の昇順（0からの連番）である（`app/ClipboardPlus/Core/HistoryFilter.swift:20-45`、`HistoryEntry.swift:135-144`）。
- **削除と取り消し**：iOS の削除は `deletion_id` と5秒後の `delete_after` を付け、5秒以内なら `undo` で戻せる（`HistoryDatabase.swift:18, 341-378, 496-505`）。

### 提案

1. **テンプレートごとの ID（`syncId`）と初回合流**
   - すべての端末で共通の **`syncId`（UUID v4、標準 `8-4-4-4-12` 表記）** をテンプレートごとに持たせる。
   - iOS では既存の整数 `id` を残したまま `template_sync_id` 列を足し、同期で既存テンプレートを更新するときは同じ行を `UPDATE` してショートカット用の整数 `id` を保つ。
   - **同一本文の統合**：初回同期や別端末での個別作成により、異なる `syncId` で本文が完全一致するテンプレートがぶつかった場合は、SQLite の一意制約に合わせて **1件に統合** する。残す `syncId` は更新時刻が新しい方（同時刻なら UUID 文字列の辞書順が小さい方）とし、名前・タグが片方だけにある場合は空でない方を補い、もう片方の `syncId` は墓標へ移して全端末の `syncId` を統一する。

2. **最後に変えた時刻（`updatedAt`）と前回同期の控え（`baseHash`）**
   - 各テンプレートに **`updatedAt`（整数 Unix ミリ秒）** を持つ。作成・移動・本文や名前やタグの編集・タグ名一括変更・並べ替えのときに更新し、コピーや貼り付けでは更新しない。
   - 各 iOS 端末は、前回 PC と同期し終えた時点のテンプレート内容ハッシュ **`baseHash`**（`kind`・`text`・`title`・`tag` から計算する SHA-256。未同期の新規作成は `null`）を保持する。
   - これにより、同期時に `現在の contentHash == baseHash` なら「この端末では前回同期から編集していない」と確実に判定でき、`baseHash == PC側の contentHash` なら「相手は編集しておらず、こちらだけが編集した」と時刻に頼らず判定できる。

3. **消したことの印（墓標）と保持期間**
   - 一度でも同期したテンプレートを削除したときは、`{ id: UUID, deletedAt: Int64, baseHash: String }` の**墓標（tombstone）**を残す（未同期のまま作ってすぐ消したものは墓標不要）。
   - **保持期間**：手動同期は端末ごとに数週間〜数か月空くことがあるため、**180日間（上限 1,000件、超えたら `deletedAt` の古い順から整理）** 保持する（1,000件でも数十KBに収まる）。180日を超えて同期しなかった端末に未削除で残っていた項目は、失われない側に倒して復活を許す。
   - **削除と未同期編集がぶつかったとき**：
     - 片方が削除し、もう片方が前回同期から編集していない場合（`hash == baseHash`、または墓標の `baseHash == PC側の hash`）は、削除を採用する。
     - 片方が古い版を見て削除した裏で、もう片方が未同期の編集をしていた場合（生存側の `hash != baseHash` かつ墓標の `baseHash != 生存側の hash`）は、**見ていない編集を消さないよう生存（編集側）を優先して残す**。

4. **タグと並び順**
   - タグのグループ順は保存せず、iOS と同じ決まり（タグ名の自然順、「その他」を最後）で表示時に並べる。C# 側は `.NET 10` 標準の `CompareOptions.IgnoreCase | CompareOptions.NumericOrdering` を使う。
   - 同じタグ内の並び順 `order` は、両側に同じ `syncId` があり本文・名前・タグが同じときは `updatedAt` が大きい方（同値なら `order` が小さい方）の `order` を採ったうえで、マージ後に残ったテンプレートを各タグの中で **`(order 昇順, updatedAt 昇順, syncId 辞書順)`** に並べ、PC 側で `0, 1, 2, ...` に振り直してから全端末へ配る。
     - 片方だけで並べ替えた場合：並べ替えた側の `updatedAt` が進むため、新しい `order` が採用される（`contentHash` には `order` を含めないため、並べ替えだけで衝突コピーが増えることはない）。
     - 両方の端末で同じタグの末尾に新テンプレートを足した場合：同じ `order` 同士が `updatedAt` 順に後ろへ並び、どちらも消えない。

5. **端末の時計がずれているときの扱い**
   - **片方だけの編集・削除**：上の `baseHash` 比較で決まるため、端末の時計が何分・何時間ずれていても、古い方が新しい編集や削除を巻き戻すことはない。
   - **連続編集・並べ替え**：ローカルで既存テンプレートを更新・削除・並べ替えするときの時刻は `max(現在時刻ms, 元のupdatedAt + 1)`（ただし元の値が現在より1年以上未来の異常値なら現在時刻へ丸める）とし、時計が遅れている端末で直後に編集・並べ替えしても必ず元の時刻より大きくなるようにする。
   - **大きな時計ずれの検知**：同期メッセージに送信端末の現在時刻 `sentAt` を入れ、PC との差が5分以上あれば計測ログに固定文（ずれ秒数のみ）を記録し、必要なら完了メッセージに「端末の時計がずれています」と添える。

6. **同じ時刻で食い違ったときの決め方**
   - 両方で別々に編集して `updatedAt` がミリ秒単位で一致した場合は、端末の種類に依存しないよう **`contentHash` の ASCII 辞書順が小さい方**（`contentHash` も同じで `order` だけ違うなら `order` が小さい方）を勝者とする。これにより、どの順でマージしても結果が一致する。

7. **両方での編集がぶつかったときに失われるものをなくす方法（案の比較と選択）**
   - 同じテンプレート（同じ `syncId`）を2台で未同期のまま別々に編集していた場合（`iOS.hash != iOS.baseHash` かつ `iOS.baseHash != PC.hash` かつ `iOS.hash != PC.hash`）、次の3案を比較した：
     - **案A（上書きのみ）**：`updatedAt` が新しい方だけを残し、古い方を捨てる。→ 時計ずれや双方での追記のときに片方の文章が失われる。
     - **案B（採用：新しい方を元の位置に残し、本文が違う古い方は「その他」に写しとして残す）**：
       - `updatedAt` が新しい方（同値なら上の決定規則）が、元の `syncId`・タグ・並び順を引き継ぐ。
       - 負けた側の**本文（`text`）が勝者と異なる場合**（かつ同じ本文の別テンプレートがまだない場合）は、新しい `syncId` を振ってタグなし（**「その他」の末尾**）に別テンプレートとして残す。名前があれば末尾に `（別の端末の編集）`（100文字以内）を付け、名前がなければ名前に `別の端末の編集` を入れて見分けられるようにする。
       - 本文が同じで名前やタグだけが変わっていた場合は、失われる文章がないため写しは増やさず、勝者の名前・タグを採用する。
     - **案C（その場で比較画面を出して選ばせる）**：狭い窓や複数端末との一括同期の途中で操作が止まるため採らない。
   - **結論：案Bを選ぶ。** 確認ダイアログで手を止めずに1回で同期が終わり、書かれた本文が失われない。

## 3. 通信の決まり

### 今のコード（確かなこと）

- **ハンドシェイクと版**：現在は第2版（`SyncProtocol.version = 2`、`app/ClipboardPlus/Core/SyncProtocol.swift:18`、`windows/ClipboardPlus.Sync/SyncProtocol.cs:16`）。`HELLO`（50バイト）・`WELCOME`（82バイト）・`AUTH`（33バイト）で共有鍵の HMAC-SHA256 と機器 ID を検証し、HKDF-SHA256 で方向別の鍵を導出する（`app/ClipboardPlus/Core/SyncHandshake.swift:7-30, 48-70`、`windows/ClipboardPlus.Sync/SyncHandshake.cs:11-30, 47-67`）。
- **暗号フレームと見出し制約**：`0x10 | 番号8バイト | AES-256-GCM暗号文 | タグ16バイト`、1フレーム最大 4 MiB（平文最大 `4,194,279` バイト）、見出しは最大 `65,535` バイトの **7ビット ASCII JSON のみ**（非 ASCII 文字は拒否）である（`SyncProtocol.swift:24-26`、`app/ClipboardPlus/Core/SyncMessage.swift:81-95, 158-164`、`windows/ClipboardPlus.Sync/SyncMessage.cs:86-108`）。
- **第2版での未知メッセージの挙動**：今の `SyncMessageCodec.decode` / `Decode` は、未知のメッセージ種別 `t` や未知の見出しキーを受けると無視せず **`format` / `Format` エラーを投げる**（`SyncMessage.swift:96, 152`、`SyncMessage.cs:109, 156`）。接続層はそのエラーで即座に接続を切断・失効させる（`app/ClipboardPlus/Services/PCSyncController.swift:724-727`、`windows/ClipboardPlus.Windows/Core/SyncCoordinator.cs:470-474`）。
- **第2版での版違いの挙動**：PC ID が一致して通信の版が違う場合、PC は版違い応答を返して `RequiresPeerUpdate = true` を出し（`SyncCoordinator.cs:315-327`）、iOS は `pauseForUpdate()` で自動再接続を止めて「両方のclipboard+を最新にしてから、もう一度つないでください」と案内する（`PCSyncController.swift:396-403, 717`、`app/ClipboardPlus/Views/SyncSettingsSection.swift:118-122`）。`protocol/make-test-vectors.mjs:42, 114` には `0x03` との版違い試験データ（`versionMismatchSamePc`）がすでに入っている。

### 提案

1. **第2版の相手とつながったときに壊れない仕組み（版を `3` に上げる）**
   - 既に出ている第2版の実装は「知らないメッセージを無視する」作りではなく、`Format` エラーで接続を切るため、版 `2` のまま新メッセージを送ると自動の履歴同期まで切断される。
   - そこで **通信の版を `3` に上げる**（`SyncProtocol.version = 3`、HMAC 先頭バイト `0x03`、HKDF info `"clipboardplus v3 pad->pc"` / `"clipboardplus v3 pc->pad"`。QR コードの書式番号 `1` はそのまま変えない）。
   - 片方だけ第2版のまま残っていた場合は、既存の版違い応答（PC ID 照合済み）によって無限再接続もクラッシュも起きず、両側の設定画面に更新案内が出て安全に止まる。

2. **同期対象の種類と上限（まずは文章・リンクを対象とする）**
   - 第1段階では定型文として使われる **文章（`text`）とリンク（`url`）** を同期対象とする（画像・ファイルのテンプレートについては「7. 決まったこと」を参照。対象外の間も iOS 側の画像・ファイルテンプレートは消さずに端末内に残す）。
   - **上限**：
     - 有効なテンプレート件数：最大 **300件**（キーボード書き出しの `templateLimit = 300`、`app/ClipboardPlus/Core/KeyboardHistoryBuilder.swift:5` と同じ）。
     - 墓標件数：最大 **1,000件**（180日間）。
     - 1件の本文（`text`）：UTF-8 で最大 **64 KiB（65,536バイト）**（約2万字）。これを超える長文テンプレートがローカルにある場合は同期から除外して端末内に残し、完了表示で件数を知らせる。
     - 名前（`title`）：100文字（書記素クラスタ単位、UTF-8 最大 400バイト、`Cc` 制御文字・改行不可）。
     - タグ（`tag`）：30文字（書記素クラスタ単位、UTF-8 最大 120バイト、`Cc` 制御文字・改行不可）。

3. **新しいメッセージの形（全件送信とページ分割）**
   - 手動ボタンを押したときだけ走るため、差分管理の状態ずれが起きない **全件スナップショット方式** にする。
   - 見出し（ASCII のみ）には操作 ID `op`（UUID）と分割番号だけを置き、日本語を含むテンプレート配列と墓標配列は **本体（`body`）に UTF-8 JSON** で入れる。

   | `t` | 方向 | その他の見出し（ASCII） | 本体（UTF-8 JSON）と意味 |
   | --- | --- | --- | --- |
   | `tpl_pull` | PC → iOS | `op` | 本体なし。PC で「同期」を押したときの送信要求 |
   | `tpl_push` | iOS → PC | `op`, `part`, `total` | iOS 側のテンプレート全件と墓標全件 |
   | `tpl_state` | PC → iOS | `op`, `part`, `total` | PC でマージ・保存した確定後のテンプレート全件と墓標全件 |
   | `tpl_ack` | iOS → PC | `op` | 本体なし。iOS 側の保存完了通知（PC 側の完了表示用） |

   - **本体の JSON 形式**：
     - 先頭ページ（`part == 0`）に `"v": 1` と `"sentAt"`（送信端末の Unix ミリ秒）を含め、各ページに `"templates": [...]` と `"tombstones": [...]` を入れる。
     - `templates` の各要素：`id`（UUID）、`kind`（`"text"` / `"url"`）、`text`、`title`（省略または文字列）、`tag`（省略または文字列）、`order`（0以上の整数）、`updatedAt`（整数ミリ秒）、および `tpl_push` のみ `baseHash`（省略または小文字16進64文字）。
     - `tombstones` の各要素：`id`（UUID）、`deletedAt`（整数ミリ秒）、`baseHash`（省略または小文字16進64文字）。
   - **分割**：
     - 1ページの本体 UTF-8 バイト数は最大 **256 KiB**、`total` は `1〜80`（全体合計の上限 20 MiB、1フレーム 4 MiB 上限の十分内側）とする。
     - 普段の使い方（数十〜百件の定型文、合計数十KB）では **`part: 0, total: 1` の1フレームだけ**で往復1〜2秒以内に終わる。長文が多いときだけ項目単位で複数ページに分けて順番に送り、全ページそろってからマージ・反映する（途中で切れたら何も書き換えない）。
   - **送信の優先順と期限**：
     - 既存の `controlFrames` → `ackQueue` → `replies` のすぐ次、**背景の履歴キュー（`pending`）より先**に送る。進行中の 32 KiB チャンクを割り込まずに、履歴の大きなファイル転送中でもすぐ同期フレームが通るようにする。
     - 同期ボタンを押してから応答完了までの待ち時間は 30秒（大きなページフレームのパケットが届き続けている間は既存の延長規則と同じく延長）とし、時間切れや切断時はエラー表示を出して待機状態を解く。
   - **暗号・認証・ログ**：
     - 既存のハンドシェイク・セッション鍵・AES-256-GCM フレーム・GATT パケット分割にそのまま乗せる。ログには操作名・件数・バイト数・所要時間だけを出し、本文・名前・タグ・ID は出さない。

### 提案

1. **保存（今の `HistoryEntry` と SQLite との関係）**
   - 画面・ショートカット・バックアップ・キーボード書き出しのすべてが `HistoryEntry` を使っているため、**`HistoryEntry` と `history` テーブル（`pinned = 1`）をそのまま維持**する。
   - SQLite を **スキーマ 6** に上げ、次を追加する：
     - `history` テーブルに `template_sync_id TEXT`・`template_updated_at INTEGER`・`template_base_hash TEXT` 列を追加する。移行トランザクションで既存の `pinned = 1` 行（取り消し待ちを含む）に UUID と `collected_at` 由来のミリ秒時刻を振る。
     - 墓標用に `template_tombstones(sync_id TEXT PRIMARY KEY, deleted_at INTEGER NOT NULL, base_hash TEXT)` テーブルを作る。
   - 作成・移動・編集・並べ替え・タグ名変更の各 SQL で `template_updated_at` を更新する。削除（`delete(id:)`）では `template_base_hash` があるテンプレートの墓標を同じトランザクションで記録し、5秒以内に `undo` されたら墓標を消して `template_updated_at` を進める（削除直後に「同期」を押しても削除が伝わり、「元に戻す」とも矛盾しない）。
   - 同期で新しく入ったテンプレートの `source` は `.written` にする（バックアップ形式 4 の互換性を保ち、iPad でそのテンプレートをコピーしたときも他のテンプレートと同じく PC のクリップボードへ送れるようにするため）。
   - バックアップ（`.clipboardplus`）と JSON 書き出しには `template_base_hash` や墓標のような同期内部状態は含めず、復元で入ったテンプレートは未同期（`template_base_hash = NULL`）として次の同期で合流させる。「組を解く」のときもテンプレート自体は残し、墓標の消去と `template_base_hash = NULL` へのリセットだけを行う。

2. **同期ボタンと結果の表示**
   - `PCSyncController` に `@Published private(set) var isSyncingTemplates = false` と `syncTemplates(completion:)` を足し、`ContentView` の同期ボタンから呼ぶ。
   - 同期結果を `HistoryStore` の反映前後から集計し、トーストで分かりやすく出す：
     - 端末側に変化があったとき：**`テンプレートを同期しました（追加 ○件・更新 ○件・削除 ○件）`**（0件の項目は省略可。「その他」に衝突の写しを残したときは `別端末の編集 ○件を「その他」に残しました` を添える）。
     - 端末側の表示は変わらず、手元の未同期変更を PC へ送っただけのとき：**`PCへ反映しました（○件）`**（「変化なし」とだけ出ると送れなかったように見えるのを防ぐ）。
     - 両側ともまったく同じだったとき：**`テンプレートは同じ状態です`**。

3. **`keyboard-history.json` への反映**
   - `HistoryStore` の直列キュー上で `applySyncedTemplates` を実行し、`needsKeyboardExport = true` を立てて `emit(.replace(try database.fetchAll()))` を呼ぶ。
   - これにより既存の `finishChanges` → `syncKeyboardFiles`（`HistoryStore.swift:789-814`）がそのまま走り、追加・編集・削除・タグ・並び順のすべてが即座に `keyboard-history.json`（テンプレート最大300件、全体2MB上限）へ書き出される。次に地球儀キーで専用キーボードを開いたときから新しいテンプレートが使える。

## 7. 決まったこと

2026年11月18日、利用者の判断により以下のとおり確定した。

1. **同期対象**：同期するのは**文章（`text`）とリンク（`url`）のテンプレートだけ**とする。画像・ファイルのテンプレートは各端末に残し、同期しない。

3. **PC の窓を開いたときの最初のタブ**：コピーした直後にすぐ貼れるよう、PC の窓（`HistoryWindow`）は**毎回「履歴」タブで開く**。

## 8. 段階2（PC 側）で決めた細かいこと

1. **保存層（`windows/ClipboardPlus.Windows/Core/TemplateRepository.cs`）**
   - `%LOCALAPPDATA%\clipboardplus\templates.json` に `FormatVersion`（`1`）、`Templates`（`Kind` は `"text"` / `"url"`）、`Tombstones`（`Id`、`DeletedAt`、`BaseHash`）を保存する。
   - 読み込み時は UTF-8 BOM を許容し、JSON 破損・版違い・読み取り不可のときは空状態で起動して落ちない。配列内の一部の項目だけが壊れている場合は、不正項目だけを読み飛ばして件数のみをログへ残す。
   - 書き込みは `templates.json.tmp` へ書き出して `Flush(true)` 後に `File.Move(..., overwrite: true)` で丸ごと置き換え、失敗時はメモリ上の状態を直前の確定状態へ戻す。
   - 作成・編集時の `Title` / `Tag` は改行や `Cc` 制御文字・孤立サロゲートを除いたうえで書記素クラスタと UTF-8 バイト上限で整え、サロゲートペアの絵文字は保つ。本文の前後空白は保ち、空白・改行のみの本文は拒否する。
   - ローカル削除時は削除前の `TemplateSyncMerge.ContentHash` を `BaseHash` に入れた墓標を記録し（180日超または1,000件超は古い順に整理）、5秒以内の「元に戻す」（`Restore`）では墓標を消して `UpdatedAt` を進め、元のグループ内位置へ戻す。
   - 「組み直す」（`App.xaml.cs` の `ExecuteRepairAsync`）では、旧 `SyncCoordinator` 停止後に `ClearTombstones()` を呼び、テンプレート本体を残して墓標だけを消す。

2. **同期制御（`windows/ClipboardPlus.Windows/Core/SyncCoordinator.cs`）**
   - Stage 2 受信時は ASCII ヘッダの `"t"` が `"tpl_*"` で始まるフレームだけ `TemplateSyncMessageCodec.Decode` へ振り分け、送信キュー `TemplateMessages` は `ControlFrames` → `AckQueue` → `Replies` の次、背景の履歴キュー `Pending` より先に送る（添付の `ActiveAttachment`・`Progress`・`HighThroughput`・`LastSent` / `LastReceived` は変えない）。
   - **iOS 起点の同期（`tpl_push`）**：全ページを受け取ってから PC の一覧とマージ・保存し、送信元の端末だけへ `tpl_state` を返す（他の接続端末へは配らない）。逆向きの `tpl_pull` / `tpl_state` や 300 件超過時は `templates.json` を書き換えずに切断する。
   - **PC 起点の同期（`SyncTemplatesAsync`）**：接続中の Stage 2 端末へ一斉に `tpl_pull(op)` を送り、全端末の `tpl_push` がそろう（または切断・30秒タイムアウトする）まで待ってから `DeviceId` 順にマージ・保存し、応答した端末へ確定済みの同一 `tpl_state` を配って `tpl_ack` を待つ。
   - **途中切断・タイムアウト・版2の相手**：2台中1台が途中で切れたり 30 秒（大きなページ受信中は延長）で応答しなかった場合は、応答した端末の分だけで保存・完了し、未完了台数を結果へ返す。接続端末が 0 台で既に版違い端末（`RequiresPeerUpdate`）を記録している場合は更新案内を返す。
   - **貼り付けと移動**：`CopyTemplateAsync` は `ownSequence` を記録して自己コピーの再収集・再送信を抑止する。`MoveHistoryToTemplatesAsync` は文章・リンクだけをテンプレートの「その他」末尾へ追加できたときに限り履歴と送信待ちから消す。ログには件数・バイト数・ずれ秒数・固定の型名だけを出し、本文・名前・タグ・ID・パスは出さない。

3. **履歴の窓の切り替えとテンプレート表示（`HistoryWindow.xaml(.cs)`・`Core/TemplateWindowLogic.cs`）**
   - 見出し帯と検索欄の間に `履歴｜テンプレート` の切り替えを置き、`Present` ごとに必ず「履歴」タブで開く（`Ctrl+Tab` でも切り替え可能）。
   - タググループは `TemplateRepository.GetGroups`（`CompareOptions.IgnoreCase | CompareOptions.NumericOrdering`、末尾に「その他」）で並べ、グループ1件または検索中は最初から開き、2件以上では閉じた状態から見出し押下で開閉する。
   - テンプレート選択・`Enter`・`Ctrl+Enter`・右クリックメニューの貼り付け／コピー・外へのドラッグは履歴と同じく窓を閉じずに動作する。削除時は `NoticeBanner` に 5 秒間の「元に戻す」ボタンを出し、追加・編集・タグ名変更は `HistoryWindow` 内の `TemplateEditorOverlay` で完結させる。

### 段階3（iOS 側）で固めた細かいこと

- **`HistoryEntry` の非変更と同期メタ情報**：`HistoryEntry` 自体は増やさず、`history` テーブルの `template_sync_id`・`template_updated_at`・`template_base_hash`・`template_dirty` 列と `template_tombstones(sync_id, deleted_at, base_hash, synced)` 表、および `TemplateSyncRowState` / `LocalTemplateSyncSnapshot` / `TemplateSyncOutcome` / `TemplateSyncError` で管理する。
- **同期中の編集取りこぼし防止**：`tpl_push` 送信から `tpl_state` 反映までの間に行われた作成・編集・並べ替え・削除は `template_dirty = 1`・`synced = 0` で区別し、`tpl_state` 反映時にも手元に残す。
- **題名・タグの送信正規化**：既存の `HistoryEntry.normalizedTag`（絵文字30文字の上限試験を維持）は変えず、同期項目生成時に制御文字の除去と `TemplateSyncMerge` の文字数・バイト数上限（題名 100 文字 / 400 B、タグ 30 文字 / 120 B）を適用する。
- **制御と画面の端末別表示**：`PCSyncController` はテンプレート同期フレームを履歴待機列より優先（制御・`ack` 系の直後）して送信し、応答待ちは30秒（大容量フレーム受信で最大180秒延長）とする。`ContentView` の同期ボタン（`accessibilityLabel("テンプレートを同期")`）は組解除中は出さず、未接続エラーや結果トースト（時計ずれ警告を含む）は `DeviceKind` に合わせて表示する。
