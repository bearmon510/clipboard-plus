# Windowsとの同期の方針

2026年11月17日。利用者がいちばんやりたいことは、iPadとWindowsのPCの間でクリップボードを同期すること。最終的には、PCでWin+Vを押すとclipboard+の履歴が開くようにしたい。

## 利用者の判断（2026年11月17日）

- 同期は両方向（iPad→PC、PC→iPad）。
- カフェや学校でも使いたい。場所ごとに設定し直すのは避けたい。
- PC側は、最終的にWin+Vでclipboard+の履歴を開く。
- App Storeへの公開は、全部がそろってから。
- TestFlightは段階ごとに出さず、まとめられるものはまとめる。

## つなぎ方：Bluetooth LE

同じWi-Fiの中で直接つなぐ方式は、カフェや学校のWi-Fiでは使えないことが多い。機器同士の通信を止めているネットワークが多いため。そこで、Wi-Fiに関係なく近くにあればつながるBluetooth LEを使う。インターネットもクラウドも通らない。

- **役割**：PCが待ち受け（GATTサーバー、peripheral）、iPadがつなぎに行く（central）。iOSのcentralは、一度つないだ相手への接続要求を出したままにでき、裏にいても相手が近づけばつながる（`bluetooth-central` のバックグラウンドモードと状態の復元）。利用者のPCのアダプターがperipheralの役割に対応していることは確かめた（LE、central、peripheral、拡張アドバタイズがすべて対応）。
- **組にする**：最初に1回だけ。PCが32バイトの乱数の鍵を作り、QRコードで表示する。iPadのclipboard+がカメラで読む。OSのBluetoothのペアリング画面は使わない。
- **暗号化**：アプリの中で行う（下の「通信の決まり」）。Bluetoothの通信を近くで傍受されても、中身は読めない。

## できること・できないこと

- PCでコピーしたものは、iPadのclipboard+が裏にいても受け取って履歴に入れられる見込み（試作で確かめる）。
- iPadでコピーしたものをPCへ送れるのは、clipboard+が集めたものだけ。iPadのクリップボードを読めるのは、clipboard+が画面に出ているときか戻ったときに限られる（iOSの制約で、これは変わらない）。
- 文章はすぐ届く。画像は数秒かかる見込み。大きなファイルは上限を決めるか対象外にする。

## 通信の決まり（第1版）

iPadとPCの両方で同じ決まりを実装する。食い違いを防ぐため、`protocol/test-vectors.json` に固定の鍵と乱数で作った通信の例を置き、両方のテストで同じ結果になることを確かめる。

### GATT

| 項目 | UUID | 性質 |
| --- | --- | --- |
| サービス | `E8DB89CB-2BBF-48DD-8D0A-FB868C9A1472` | PCがアドバタイズする |
| PCへ（iPad→PC） | `F4508CC7-393F-4288-8B72-A4A9A09D1D4D` | write、write without response |
| iPadへ（PC→iPad） | `3A7ADCFC-CD62-4AF8-BF09-2C73023C5B83` | notify |

### 分割

1回の書き込みや通知（パケット）で送れる大きさには上限がある（接続ごとのMTUで決まる）。フレームをパケットに分けて送る。パケットの先頭1バイトは印で、bit0がフレームの始まり、bit1がフレームの終わり。残りが中身。1つの接続の中では順番どおりに届く前提で組み立て直す。組み立てに失敗したら接続を切り、まだ確認の返事がないものを次の接続で送り直す。

### 接続の確認と鍵

- 組にした鍵 `K`（32バイト）を両方が持つ。
- iPad→PC：`HELLO` = 種別 `0x01`、版 `0x01`、iPadの識別子16バイト、乱数 `Ni` 32バイト。
- PC→iPad：`WELCOME` = 種別 `0x02`、版、PCの識別子16バイト、乱数 `Np` 32バイト、`HMAC-SHA256(K, "pc" ‖ Ni ‖ Np)`。
- iPad→PC：`AUTH` = 種別 `0x03`、`HMAC-SHA256(K, "pad" ‖ Ni ‖ Np)`。
- どちらかの確かめに失敗したら切る。iPadは、その相手を組の相手ではないとして、しばらく無視する。
- 向きごとの鍵：HKDF-SHA256（鍵 `K`、salt `Ni ‖ Np`、info `"clipboardplus v1 pad->pc"` または `"clipboardplus v1 pc->pad"`、32バイト）。

### データ

- フレーム：種別 `0x10`、番号8バイト（ビッグエンディアン）、暗号文と認証タグ。
- AES-256-GCM。nonceは0が4バイトと番号8バイト。AADは種別と番号の9バイト。番号は向きごと・接続ごとに0から1ずつ増やす。増えていない番号は捨てて接続を切る。
- 平文：見出しの長さ2バイト（ビッグエンディアン）、見出し（UTF-8のJSON）、本体のバイト列。
  - 項目：`{"t":"item","id":"<UUID>","kind":"text","at":<ミリ秒>,"from":"pad"|"pc"}`、本体は文章のUTF-8。画像は後の版で `kind:"image"` と型を足す。
  - 確認：`{"t":"ack","ids":["<UUID>", ...]}`、本体なし。
  - 生存確認：`{"t":"ping"}`。
- 送った項目は、確認が来るまで手元に残し、つなぎ直したら送り直す。受け取った側は、見たことのある `id` を無視する。

### 自分の書き込みを拾わない

- PC：受け取った項目をWindowsのクリップボードに入れたら、そのときのクリップボードの通し番号を覚えておき、その変化は送り返さない。
- iPad：受け取った項目は履歴に直接入れる。iPadのクリップボードにも入れる設定のときは、既存の自己コピーの仕組みで、その変化を履歴へ二重に入れない。

### 第1版の実装でそろえる細部（2026年11月17日追記）

- **組にする情報**：QRの文字列は `clipboardplus-pair:1:<PCの識別子 base64url>:<鍵 base64url>:<PCの名前 パーセントエンコード>`。コロンで区切った5部分だけを認め、前後の空白や追加部分は認めない。識別子は16バイト、鍵は32バイト。base64urlはパディングの `=` なし（それぞれ22文字・43文字）で、未使用ビットも0の正規の表記だけを受け付ける。名前はUTF-8で1〜255バイト、U+0000〜U+001FとU+007Fを禁止する。名前のASCII英数字と `-._~` だけをそのまま書き、ほかのUTF-8バイトは `%HH`（出力は大文字）にする。読み取りでは16進文字の大文字小文字と、英数字等を `%HH` にした表現も許すが、生の空白・`+`・非ASCII文字、不完全な `%`、不正UTF-8は禁止。文字列全体の最大長は853 ASCII文字。
- **識別子**：機器の識別子は最初にUUID v4を生成して保存し、接続ごとには変えない。16バイトの転送順はUUIDのハイフンを除いた16進表記の左から順（RFC 4122の順）で、Windowsの従来の `Guid.ToByteArray()` の混在エンディアン順は使わない。入力は任意の16バイトを受け付ける。項目のUUIDも新規作成時に生成して保存し、再送で変えない。JSONへの出力は大文字・ハイフン付き36文字、入力では大文字小文字を区別しない。
- **接続の確認**：HELLOは50バイト、WELCOMEは82バイト、AUTHは33バイトちょうど。異なる版・種別・長さや順序違反はエラー。iPadはWELCOMEのPC識別子がQRの識別子と一致することも確認する。PCは既知のiPad識別子があれば一致を確認できる。識別子自体は上記HMACの入力に含まれないため、鍵の所持の確認と識別子の比較を区別する。PCはAUTH成功まで相手の識別子と通信鍵を確定しない。iPadはWELCOMEの確認後にAUTHと通信鍵を得るが、必ずAUTHを先に送ってからデータを送る。実運用のK・Ni・Npは暗号学的乱数とし、Ni・Npは接続ごとに新しく生成する。固定値の注入はテスト専用。
- **フレームと番号**：AES-GCMの認証タグは16バイトで暗号文の直後に置く。4MiB（4,194,304バイト）は種別・番号・暗号文・タグを含めたフレーム全体の上限で、平文の最大長は4,194,279バイト。番号は符号なし64ビット。最初の受信番号は0以外でも受け付け、その後は直前より大きい番号だけを受け付ける（欠番は許す）。送信は必ず0から始めて1ずつ増やし、最大値を送った後は新しい接続が必要。認証成功後だけ受信番号を更新する。
- **パケット**：APIに渡す上限は印の1バイトを含むGATT値の最大バイト数（ATT MTUそのものではない）。最低2バイト必要。空フレーム・印だけのパケット・予約ビットbit2〜7・組み立て中の再度の始まり・始まりのない続きや終わり・パケット上限超過・組み立て上限超過はエラー。1パケットで完結するときは印 `0x03`。未完の始まりは到着時点では正当なので、切断・タイムアウト時に `finish` / `Finish` を呼んでエラーとして検出する。タイムアウトの時計と切断処理は次の接続層の担当。
- **見出しと本体**：見出しの出力はキーを辞書順に並べ、空白なしのJSON。見出しの最大長は65,535バイト。ASCII制約は転送バイトと、JSONエスケープを読み取った後の文字列・キーの両方に適用する。読み取りはキーの順・JSON標準の空白・ASCIIのJSONエスケープに寛容にする。重複キー・未知のキー・未知の種別・コメント・末尾カンマ・末尾の余分なJSONは禁止する。JSONの入れ子は最大8段。`at` は1970年からのミリ秒の整数で、範囲は −9,007,199,254,740,991〜9,007,199,254,740,991（JavaScriptでも整数を正確に表せる範囲）。小数・指数表記・文字列・真偽値は受け付けない。`from` は `pad` または `pc`、`kind` は `text` のみ。文章は厳密なUTF-8で空文字も許す。確認の `ids` は1〜1,024件（重複は許す）。確認・生存確認は本体を持たない。
- **エラーと寿命**：両実装のエラー区分は形式、上限、パケット、状態、認証、相手識別子、番号。受信側の組み立て・接続確認・復号でエラーが起きたオブジェクトは再使用できない。接続層はどの受信エラーでも接続を切り、平文の読み取りエラーでも同様に切る。オブジェクトは接続・方向ごとに1個作り、呼び出しを直列にする。同じ通信鍵で送信器を作り直して番号を0に戻してはならない。再接続では新しい乱数から新しい鍵を得る。試験データにだけ入る固定鍵は公開値で、実運用に使わない。
- **今回のPCライブラリ**：通信の中核とテストはOS非依存の `net10.0`。下記「置き場所」のWindows用ターゲットは、今後のBluetooth・常駐アプリ層で使う。
