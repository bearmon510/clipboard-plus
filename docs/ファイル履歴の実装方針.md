# ファイル履歴の実装方針（0.11.0・画面以外）

2026年11月16日。Swift 5言語モード、iOS 17以上。Foundation、UIKit、UniformTypeIdentifiers、CryptoKit、SQLite3のみを使用し、外部ライブラリは追加しない。

## 判定と収集

- `HistoryKind.file` と `HistoryFile` を追加。元のファイル名、保存用の名前、型識別子、バイト数、SHA-256を保持する。`HistoryEntry.file` はOptionalで、旧JSONにキーがなくても読める。ファイルの `text` は空文字。
- `HistoryFileTypes.preferred(in:)` は、提供順で最初の対象型を選ぶ。`public.data` または `public.content` に適合し、text・url・image・directoryに適合しないものが対象。`dyn.`、UIKit／pasteboard／private／Notesの内部型、アプリ自身の型を除外する。RTFD／flat-RTFDも明示的に文章側へ分類する。
- 既存の画像優先は維持する。その次に文章・通常URLの表現を優先する。RTF／HTML／RTFDが提供されていれば、プレーン文字列を読めなくてもファイルへフォールバックしない。メモの文章に付属する内部データをファイルにしないため。`hasStrings == true` の場合も文章側へ進める。
- **文字のファイル（0.11.1、利用者の要望）。** .txt・.csv・.html・.rtfなど、中身が文字のファイルもファイルのまま残す。目印は、プロバイダーの `suggestedName` に文字の拡張子があり、そのプロバイダーが文字の型を出していること（`HistoryFileTypes.namedTextFile(types:suggestedName:)`）。編集中の文章のコピーには名前が付かないので、文章として入る。通常URL・画像・秘密の印があれば対象にしない。この判定は `hasStrings` より先に行う。保存できる型の判定は `isStorable`（文字の型を含む）、名前なしでファイルとみなす型は `isFile`（文字の型を除く）に分けた。計測ログには名前を書かず、拡張子だけを `名前=` として残す。「ファイル」アプリが実際に名前を付けるかは実機で確認する。
- `public.file-url` 自体はファイルの本体として取り込まず、参照先URLを開かない。ただしPDF等の具体的な本体表現と同梱されている場合、その型の選択を妨げない。通常URLや文章も同梱されていれば、そちらを優先する。
- 自動収集は `UIPasteboard.itemProviders` を使用し、プロバイダーの登録型を優先して選ぶ。pasteboard.typesも除外判定に含める。自動収集で複数項目がある場合は最初の対象ファイル1件。手動のプロバイダー受信とドロップは各プロバイダーを個別に処理する。
- `suggestedName` を元の名前に使う。パスの区切り・制御文字を除去し、240文字までとする。空の場合は型の拡張子から「ファイル.pdf」などを作る。名前は表示用であり、保存先パスに使わない。
- `loadFileRepresentation(forTypeIdentifier:completionHandler:)` の完了ハンドラ内で、提供URLが有効な間に一時領域へ逐次コピーする。大きなDataへ読み込むフォールバックは設けない。ファイル表現を提供できなければ、型一覧と読み込み失敗を記録する。
- 上限は **50,000,000 bytes（十進50MB）**。ファイルの属性と実際に読み取ったバイト数の両方で確認する。64KiBずつ読み書きし、SHA-256も逐次更新する。0バイトのファイルは許可する。ディレクトリ・パッケージ・シンボリックリンクは取り込まない。
- 非同期読取の開始時と終了時で `changeCount` が異なる結果は破棄する。どのコピーに属する本体か確定できないため。新しいchangeCountは次の監視で対象になる。古い結果の破棄で、新しく記録された自己コピー印を消さない。

## 保存・重複・削除・使用量

- DBスキーマを2から3へ移行。`file_hash / file_name / original_filename / file_bytes / file_type` を追加する。文章の一意インデックスからimageとfileを除き、fileは有効行のハッシュで一意にする。既存v1→v2→v3の順で移行できる。旧アプリはschemaVersionの上限チェックでv3のDBを拒否する。
- 同じハッシュは1件にまとめ、回数・最終収集日時・経路を画像と同じ規則で更新する。名前や型が違っていても、最初に保存したメタデータを維持する。画像とファイルのハッシュ領域は別。
- 保存名は `SHA256-UUID.拡張子`。UUIDを付けることで、重複取り込み、取り消し待ち、復元のロールバックが別の本体を上書きしない。
- 本体は既存のApplication Support内 `HistoryImages` ディレクトリに置く。名称は互換性のため維持し、画像・ファイル共通の添付データ領域として使う。`HistoryFileFiles` がファイルの取り込みを担当する。
- `HistoryEntry.attachmentFilenames / attachmentByteCount` を通じ、保存待ち、起動時の孤立ファイル掃除、全削除、取り消し、期限削除、バックアップ中の保護に両方を含める。既存の `referencedImageFiles()` は名前を維持し、ファイルも含む参照集合を返す。
- 通常削除・全削除では画像と同じく5秒間本体を残し、取り消し期限後に物理削除する。取り消し中の再収集もハッシュでマージする。期限削除と件数・容量による削除は即座に掃除対象となる。
- 既存の未ピン留め1,000件上限は全種類共通。既存500MB上限を**未ピン留めの画像＋ファイルの合計**に適用する。ピン留めは容量削除からも除外する。実装上の引数名 `imageByteLimit` と定数名 `HistoryImageFiles.maximumTotalByteCount` は既存呼び出し互換のため維持する。復元の見積もりも同じ合計値を使う。
- `monitor.imageUsage: HistoryImageUsage` は画像のみのまま。`monitor.fileUsage: HistoryFileUsage` を追加し、`count / byteCount` でファイルの件数と容量を返す。取り消し待ちも使用量へ含む。画面で合計を出す場合は両方を足す。一時的な受信・コピー・バックアップ領域はこの値に含まない。
- 保存失敗時は本体を保持したメタデータの保存待ちキューを再試行する。重複として使われなかった本体は掃除する。

## コピー、ドラッグ、ドロップ、ショートカット

- `monitor.copy(_:, completion:)` はファイルでも利用できる。URLで登録した `NSItemProvider` に元の名前を `suggestedName` として設定し、`setItemProviders(_:localOnly:expirationDate:)` で書き込む。型は元の識別子。画像と同じハッシュ＋changeCountの入場判定を別インスタンスで使い、自己コピーの読み戻しを加算しない。後日の外部コピーは加算する。
- コピー・ドラッグ用にはストアの直列キューで一時コピーを作る。プロバイダーがその寿命を保持するため、履歴削除や5分経過後に遅れて読み出されても本体を提供できる。元ファイルの削除は妨げない。一時領域は既存 `BackupTemporaryFiles` のプロセスディレクトリ内とし、通常は所有者解放時、残骸は次回起動時に掃除する。
- `monitor.rowProvider(_:)` はファイルに対応。ドラッグにだけ既存のownProcessの行マーカーを付け、自分の行の再ドロップは無視する。コピー用には行マーカーを付けない。
- 既存画面が読む `HistoryImageLoader.contentTypes` に `.data / .content` を追加した。`.onDrop` 側の型一覧を変更する必要はない。受信後の判定は広い受付型とは別に厳密に行う。
- `HistoryEntryEntity.file: IntentFile?` を追加。URLで構築して全本体をまとめてメモリへ読み込まず、ファイル名とサイズを表示する。`HistoryFilterOption.files` が「履歴を取り出す」の選択肢になる。「履歴をコピー」は既存の `copyForShortcut` → `copy` 経路で対応する。
- `ShortcutIntents.swift`、特に `ClipboardPlusShortcuts` は今回編集していない。

## バックアップの互換性

- ファイルを含む `.clipboardplus` はバイナリヘッダーとマニフェストの版を **2** にする。ファイルを含まない場合は従来の版1のまま出力する。読み取りは版1・2に対応し、ヘッダーとマニフェストの一致も検証する。
- 版2も `CLIPPLUS`、big endian UInt64の版、JSON長、JSON、項目順の本体長＋本体という形式。画像のサムネイルは従来どおり復元時に再生成する。ファイルも長さ・上限・型・ハッシュを確認し、バックアップ由来の保存パスは使用しない。
- **旧アプリは新版バックアップを明確に拒否する。** 変更前の `HistoryBackup.validate` はJSONを読む前に `readNumber(...) == 1` を要求し、不一致なら `BackupError.version`（「このバックアップの版には対応していません。」）を返す。未知のfile項目を部分的に復元する動作にはならない。旧版の実行環境での実行確認はしていないが、旧ソースのヘッダーチェックと新版ヘッダーのXCTestを用意した。
- メタデータだけの従来JSON書き出しは、fileを含むとformatVersion 3、含まなければ2。本体を含まないため、完全な復元には `.clipboardplus` を使用する。
- 復元の内容キーは `file:hash`。画像と同じ最小保存日時・最大最終日時・最大回数・ピンORの規則。新規本体の配置をDBのCOMMIT前に行い、失敗時にはSQLと今回配置した本体を戻す。バックアップ作成中のファイルも既存の保護集合に含める。

## プライバシーと計測

- `ClipboardPrivacy` のConcealed／Transient／AutoGeneratedの印を維持。自動収集はpasteboardと全プロバイダーの型、手動受信とドロップは受信したプロバイダー全体の型を、本体を読む前に確認する。
- 読取成功、型の対象外、上限超え、読み込み失敗、非同期読取中の変更を記録する。pasteboard.types、登録型一覧、選択型、経路、所要ms、バイト数、ハッシュ先頭8文字、判断理由を残す。
- 本体・パス・NSErrorの詳細はログへ渡さない。ファイル名は既存の文章と同じく MeasurementEvent.text に渡し、通常は記録しない。利用者が既存の文章プレビューをONにした場合のみ、保存・自己コピーのログへ名前の先頭20文字を出す。型・サイズなどのdetails欄には名前を入れない。本体はプレビューONでも記録しない。
- 利用者への短い通知は `monitor.fileNotice: String?`。既存の `imageNotice` は画像用のまま。ファイル読み込みの保留も既存 `pendingSaveCount` に含む。

## 検証と残る確認

XCTestを21件追加。判定（PDF／zip／動画、RTF／HTML／RTFD／URL／画像／動的型／内部型）、50MB境界、名前・ハッシュ、v2移行、検索・フィルター、重複、自己コピー、非同期変更、プライバシー、通知、ドロップ・削除後のドラッグ、削除・全削除・取り消し・期限削除、容量、バックアップの保護・往復・冪等性・旧版の読取・破損拒否・配置失敗のロールバック、ショートカットの表示・本体・コピーを対象とする。XCTestの完了ハンドラからthrowしない構成。

Windows上ではSwiftソースから取り出したSQLをPython標準SQLiteで実行し、v1/v2→v3移行、移行失敗のロールバック、ファイルINSERTの8バインド、ハッシュ一意性、空本文との分離、回数更新、取り消し時の重複解消、使用量、20カラムの読取位置を確認した。新規5ファイルのUTF-8・末尾改行・余分な空白と、変更差分の git diff --check も確認した。これはSwiftの型チェックやXCTestの成功を意味しない。

このPCではSwift／Xcodeを実行できないため、**シミュレータ・実機向けReleaseのビルドとXCTestは未実行**。CIのXcode 27.1／iOS 27 SDKで両ターゲットと既存テストを含むXCTestの実行が必要。

実機で未確認：

1. iOS 17と現行iPadOSの「ファイル」（ローカル／iCloud／外部プロバイダー）、メモ、Safari、「写真」の動画が提供する型の組み合わせ、順序、suggestedName、hasStrings。
2. 「写真」の動画に画像プレビューも同梱される場合は、現方針では画像が優先される。型ログを見て必要なら判定を調整する。
3. 「ファイル」がfile-urlや内部型だけを提供する場合は保存しない。本文表現がなければ、URL参照先へのアクセスで補完しない。
4. ファイルをコピーし直した際の「ファイル」アプリへの貼り付け、元の名前・拡張子・型、他アプリへのドラッグ、遅延読取、Handoff。
5. 大きな動画・クラウドファイルの取得時の待ち時間、メモリ、バックグラウンド中断、プロセス終了後の一時領域回収。アプリ側の逐次処理は64KiBだが、提供元やOS内部のメモリ使用量までは保証できない。
6. Shortcutsの実際のプロパティ表示・ファイル引き渡し、およびClaudeが作るQuickLook等の画面。
